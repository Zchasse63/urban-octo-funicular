# Bugs Discovered — Asset System (Episode Detail, Assets Tab)

**Feature:** episode-detail (Assets tab) + content pipeline
**Discovered by:** live-walkthrough during product-quality audit
**Date:** 2026-04-15
**Dev server:** `next dev` (Turbopack) against Supabase project `itnzbdojxvbhuxnwqgzg`
**Test user:** `live-test@podbrain-test.local` (agency tier, active)
**Episode under test:** `e3e5fc46-a302-4533-af7e-3f714f540712` — `[TEST] Planet Money 25min — fix verification`

**Observed state:** Assets tab header reads **"4 of 14 assets generated"** while the UI simultaneously displays **10+ "Ready" badges**. The Generate-All button is enabled (because 4 ≠ 14) and the DB contains 8 generated_assets rows for this episode. Three numbers, three different stories.

---

## Root cause overview — three-way slug drift

There are **three independent vocabularies** of asset-type slugs in the codebase, and they don't agree with each other:

| Source | File | Count | Notes |
|---|---|---:|---|
| Canonical registry | `app/src/lib/assets/asset-types.ts` | 37 | The "30+ content assets" marketing claim points here |
| Constants list (synced with DB enum) | `app/src/lib/constants.ts:77` | 42 | Has intentional duplicates (`newsletter` AND `newsletter_email`, `quote_card` AND `quote_cards`, `tiktok_hook` AND `tiktok_hooks`, `audiogram` AND `audiogram_clips`) as a workaround for upstream drift |
| UI display map | `episode-detail.tsx:1035 UI_ID_TO_DB_TYPE` | 14 | Only surfaces 14 of the 37 registry types |
| Actual seed pipeline writer | `app/src/app/api/seed/route.ts:373–467` | 17 | Writes a fourth vocabulary |

The duplicate entries in `constants.ts` are the smoking gun: whoever wrote that file already knew there was slug drift and added both variants so the type-check passes regardless of which part of the codebase writes which slug.

## Bug #13 — UI map expects wrong slugs; 3 mappings are guaranteed orphans

**Severity:** HIGH — content generated by the pipeline is silently dropped from
the UI because the display-map slugs don't match the pipeline-writer slugs.
Users who legitimately generated Instagram, audiogram, or AI-summary content
see those rows stuck at "Idle" forever.

**File:** `app/src/components/episodes/episode-detail.tsx:1035-1050`

```ts
const UI_ID_TO_DB_TYPE: Record<string, string> = {
  'show-notes':         'show_notes',         // ✅ matches pipeline
  'chapter-markers':    'chapter_markers',    // ✅ matches pipeline
  'episode-description':'seo_description',    // ✅ matches pipeline
  'twitter-thread':     'twitter_thread',     // ✅ matches pipeline
  'linkedin-post':      'linkedin_post',      // ✅ matches pipeline
  'instagram-captions': 'instagram_caption',  // ❌ pipeline writes 'instagram_carousel'
  'blog-post':          'blog_post',          // ✅ matches pipeline
  'newsletter':         'newsletter_email',   // ✅ matches pipeline (constants.ts has both)
  'guest-bio':          'guest_bio_short',    // ✅ matches pipeline
  'guest-email':        'guest_promo_kit',    // ✅ matches pipeline
  'audiogram-script':   'audiogram_clips',    // ❌ pipeline never writes this slug
  'youtube-desc':       'youtube_description',// ✅ matches pipeline
  '1-liner':            'ai_summary_short',   // ❌ pipeline never writes this slug
  'tldr':               'key_takeaways',      // ✅ matches pipeline
};
```

**Three guaranteed orphans** — UI rows that can NEVER display real content:
1. `instagram-captions` — expects `instagram_caption`, pipeline writes `instagram_carousel`
2. `audiogram-script` — expects `audiogram_clips`, pipeline never writes any audiogram slug (audiogram lib is a scaffold per CLAUDE.md: "Audiogram Script" is Tier-4 pending Remotion dependency)
3. `1-liner` — expects `ai_summary_short`, pipeline never writes any AI-summary slug

**Evidence for Instagram mismatch** — from `app/src/app/api/seed/route.ts:425`:
```ts
assets.push({
  episode_id: episodeId,
  asset_type: 'instagram_carousel',  // ← carousel, not caption
  content: carousel,
  metadata: { platform: 'instagram', slide_count: 6 }
})
```

The `instagram_caption` slug does exist in `constants.ts:100` but NO code path actually inserts it. The UI is looking up a key that will never be populated.

**Fix:**

Option A (minimal, preserves current layout):
```ts
'instagram-captions': 'instagram_carousel',  // fix the slug
// remove 'audiogram-script' and '1-liner' entirely, OR add corresponding pipeline writers
```

Option B (structural, preferred): **Delete `UI_ID_TO_DB_TYPE` entirely** and derive the UI list from `asset-types.ts`. The `assetMap` becomes a trivial `Map<string, GeneratedAsset>` keyed by DB `asset_type`, and the UI iterates over whatever the registry says exists. This eliminates the drift class of bugs forever.

## Bug #14 — `ASSET_CATEGORIES` hardcodes `status: 'generated'` on 6 rows; rows with no DB match become phantom "Ready" states

**Severity:** HIGH — UI lies to the user. "Ready" badge on a row with no
content, Copy button produces an empty string when clicked, Download button
writes a zero-byte .txt file.

**File:** `app/src/components/episodes/episode-detail.tsx:637-777`

The `ASSET_CATEGORIES` array is a hand-maintained mock of the asset list with literal status strings baked in. 8 of the 14 rows are hardcoded `status: 'generated'` and 6 are hardcoded `status: 'idle'` — these values have nothing to do with actual DB state.

```ts
const ASSET_CATEGORIES: AssetCategory[] = [{
  id: 'core',
  assets: [
    { id: 'show-notes',         label: 'Show Notes',          status: 'generated', ... },  // line 648
    { id: 'chapter-markers',    label: 'Chapter Markers',     status: 'generated', ... },  // line 655
    { id: 'episode-description',label: 'Episode Description', status: 'generated', ... },  // line 662
  ]
}, {
  id: 'social',
  assets: [
    { id: 'twitter-thread',     label: 'X Thread',           status: 'generated', ... },  // line 676
    { id: 'linkedin-post',      label: 'LinkedIn Post',      status: 'idle',      ... },  // line 683 ⚠️
    { id: 'instagram-captions', label: 'Instagram Captions', status: 'idle',      ... },  // line 690
  ]
}, {
  // ...
  { id: 'audiogram-script',     label: 'Audiogram Script',    status: 'generated', ... },  // line 746 ⚠️
  // ...
  { id: '1-liner',              label: 'One-liner Summary',   status: 'generated', ... },  // line 767 ⚠️
  { id: 'tldr',                 label: 'TL;DR Bullets',       status: 'generated', ... },  // line 774
}];
```

**Then `AssetRow` initializes its local state with `realAssetContent ? 'generated' : asset.status`:**

```ts
// episode-detail.tsx:799
const [status, setStatus] = useState<AssetStatus>(
  realAssetContent ? 'generated' : asset.status
);
```

This creates two failure modes:

### Failure mode A — phantom "Ready" (hardcoded 'generated' + no DB match)

Three rows will render "Ready" on EVERY episode, regardless of DB state, because they're hardcoded `'generated'` AND their UI map slug cannot match any pipeline output (see BUG #13):
- `audiogram-script` — always phantom
- `1-liner` — always phantom
- `instagram-captions` — NOT hardcoded 'generated' (it's 'idle'), so not in this bucket. Scratch it.

Three additional rows hardcoded `'generated'` are vulnerable to the phantom state on ANY episode where the pipeline didn't run that specific step:
- `show-notes`
- `chapter-markers`
- `episode-description`
- `tldr`

### Failure mode B — hidden "Generated" (hardcoded 'idle' + DB match exists)

Then there's the opposite failure: two rows hardcoded `'idle'` that MIGHT have real content:
- `linkedin-post` — hardcoded `'idle'` at line 683, but pipeline writes `linkedin_post` slug
- `newsletter` — hardcoded `'idle'` at line 711, but pipeline writes `newsletter_email` slug

These are saved by the `realAssetContent ? 'generated' : asset.status` fallback: if the assetMap lookup succeeds, the row flips to `'generated'` via the ternary, so users DO see the content. But the `ASSET_CATEGORIES` hardcode is still misleading as source-of-truth.

### Concrete evidence of phantom rows on the test episode

Test episode `e3e5fc46-a302-4533-af7e-3f714f540712`:
- DB has 8 generated_assets rows
- UI header reads "4 of 14 assets generated" → `assetMap.size === 4`
- UI renders 10+ "Ready" badges → 6 of those are phantom (hardcoded 'generated' without DB content)

**To verify:** Click Copy on the "One-liner Summary" or "Audiogram Script" row. The clipboard payload is an empty string because `contentText = realAssetContent || asset.content || ''` resolves to `''` — neither the DB nor the hardcoded ASSET_CATEGORIES provides content.

```ts
// episode-detail.tsx:813
const contentText = realAssetContent || asset.content || '';
const handleCopy = () => {
  navigator.clipboard.writeText(contentText);  // writes ''
  setCopied(true);
};
```

The Download button has a guard (`if (!contentText) return;` at line 820), so it silently no-ops instead of writing a zero-byte file. Copy does NOT have the guard — it copies the empty string to the user's clipboard and flips the "Copied!" toast for 1.8s, making the user think they got content.

**Fix:**

```ts
// ASSET_CATEGORIES should have NO status field at all. Remove it from all 14 rows.
{
  id: 'show-notes',
  label: 'Show Notes',
  icon: FileText,
  description: 'Full editorial show notes with timestamps',
  // status: 'generated',   ← DELETE
  accentColor: 'text-emerald-600',
}

// AssetRow initialization becomes simply:
const [status, setStatus] = useState<AssetStatus>(
  realAssetContent ? 'generated' : 'idle'
);
```

This single change eliminates all phantom "Ready" badges across every episode in the system.

## Bug #15 — Counter mismatch: "4 of 14" header disagrees with visible "Ready" badge count

**Severity:** MEDIUM — not a data corruption bug, but a credibility killer. A user who sees "4 of 14 assets generated" and then counts 10 green badges immediately assumes the app is broken. They're right, but for a different reason than they think.

**File:** `app/src/components/episodes/episode-detail.tsx:1083-1088`

```ts
const generatedCount = ASSET_CATEGORIES.reduce((sum, cat) => {
  return sum + cat.assets.filter(a => {
    if (assetMap.has(a.id)) return true;   // ← only counts real DB matches
    return false;
  }).length;
}, 0);
```

vs. `AssetRow` at line 799 which also considers the hardcoded `asset.status` for display:

```ts
const [status, setStatus] = useState<AssetStatus>(realAssetContent ? 'generated' : asset.status);
```

These two code paths use different inputs to decide "is this asset generated?":
- **Header counter:** assetMap (DB) only
- **Badge rendering:** assetMap (DB) OR hardcoded literal `'generated'`

The counter is actually the TRUSTED number here — it reflects real DB state. The badges are the liars. Fixing BUG #14 (removing the hardcoded status values) automatically fixes this mismatch because both code paths will then agree.

**Fix:** Same as BUG #14 — removing the hardcoded `status` field makes both counters converge.

## Bug #16 — `"30+ content assets"` marketing claim is unreachable in the UI

**Severity:** LOW (marketing drift, not a functional bug)

The landing page and `CLAUDE.md` both advertise "30+ content assets" per episode. The canonical registry at `app/src/lib/assets/asset-types.ts` does define 37 types. However:

- The UI surface in the Assets tab (`ASSET_CATEGORIES`) only renders **14** of them
- The pipeline writer (`api/seed/route.ts`) only generates **17** of them
- Of the 37 registered types, **23 have no UI path whatsoever** (no "Generate" button, no display row)

Examples of registered-but-unreachable types:
`episode_titles`, `transcript_summary`, `linkedin_post_host`, `linkedin_post_guest`, `linkedin_article`, `twitter_single`, `instagram_reel_script`, `tiktok_script`, `youtube_shorts_script`, `youtube_title_tags`, `infographic_outline`, `discussion_questions`, `poll_ideas`, `call_to_action`, `podcast_teaser`, `cross_promo_script`, `medium_article`, `substack_post`, `ai_summary_detailed`, `highlight_reel`, `press_release`, `quote_cards`, `tiktok_hooks`

**Fix options:**
1. **Honest:** update marketing copy to "14 content assets across 6 categories" (what the UI actually delivers today). Least disruptive.
2. **Ambitious:** build Generate buttons for the remaining 23 types so the UI actually reaches 37. This is the "phase 2" version of content multiplication — material scope.
3. **Middle ground:** expose the full registry behind a "More asset types" dropdown or "Advanced" accordion. Keeps the default UI clean while not lying about coverage.

Recommendation: ship Option 1 to get honest, then evaluate Option 2 post-launch based on user demand.

---

## Shared fix direction

All four bugs above (#13, #14, #15, #16) collapse into a single structural refactor:

1. **Delete `ASSET_CATEGORIES`** from `episode-detail.tsx`.
2. **Delete `UI_ID_TO_DB_TYPE`** from `episode-detail.tsx`.
3. Make the Assets tab iterate directly over `asset-types.ts` registry entries (or a curated subset if you keep the "14 visible" default).
4. Drive all row state exclusively from the `assetMap` (DB-backed). Rows with no DB entry start as `'idle'`.
5. Add a lint rule or runtime assertion that every registered asset type has either a UI row OR is explicitly marked as "backend-only."
6. Delete the duplicate slugs in `constants.ts` (`newsletter` vs `newsletter_email`, etc.) once the registry is the single source of truth.

After that refactor, the Assets tab is a thin view over the registry and the generated_assets table. The drift class of bugs becomes structurally impossible.
